## Найденные и устранённые дефекты (важно для M2)

1. **BEP 44 требует `verify` в конструкторе bittorrent-dht** — иначе все ноды отвергают mutable-put
   («verification not supported» → у клиента «All queries failed»). Добавлен `bep44Verify(sig, value, pk)`.
2. **Порядок аргументов sodium-native** `crypto_sign_verify_detached(sig, message, pk)` → boolean
   (не выходной буфер) — без этого нода падала на первом входящем put.
3. **Тайминг старта**: put/get сразу после `ready` идут в пустую таблицу маршрутизации →
   exit: первый publish через 2 c + retry 5 c на неудачу; клиент: lookup 3 c до первого offer,
   10 c после.

## Найденные и устранённые дефекты M2/M3

4. **`get` mutable-элемента требует соль в opts**: `dht.get(TARGET, { salt }, cb)` — иначе
   `r.salt` пуст, подпись/target никогда не сходятся → «no result» (libtorrent/bittorrent-dht API-нюанс).
5. **Окно свежести offer'а должно быть больше интервала републикации** (было: окно 5 мин,
   републикация 10 мин → offer отбрасывался). Стало: републикация 5 мин, окно 12 мин.
6. **Фильтрация публичных DHT bootstrap с клиентской сети**: 3 из 5 (router.bittorrent.com,
   router.utorrent.com, router.bitcomet.com) не отвечали UDP; dht.transmissionbt.com,
   dht.libtorrent.org — живы. Сам-hosted bootstrap на VPS (magnetgate-dht:20001, сам бутстрапится в
   публичную DHT) решил проблему — ровно как предусмотрено в §4 тест-гайда / §3.1 PoC-дока.
7. **systemd `${PSK}` + PowerShell**: `\${PSK}` в heredoc → systemd не развернул переменную
   (порт съехал); unit-файл безопаснее готовить локально и деплоить файлом.

## Поправка по топологии (WireGuard на клиентской машине)

После M3/M4 уточнена реальная топология клиентской машины. Постоянно активен WireGuard-адаптер
`telegram-femida4me-wg1` (дефолт-маршрут, метрика 0), схема двухколенная:

```
PC ──WG──► Beget VPS (RU, 217.12.38.106) ──► за границей: туннель-splitter (делит RU/foreign трафик)
```

Следствия для протокола испытаний:

- Весь PoC-трафик (DHT UDP + дата-канал) шёл **внутри этой схемы**, т.е. M2/M3-замеры =
  «наш транспорт поверх WG-инфраструктуры пользователя», а не поверх сырого ISP.
- «Direct»-замеры (TC-09 прямые, пинги bootstrap) выполнялись с выхода этой связки;
  фильтрация 3/5 публичных DHT-bootstrap относится к пути Beget→(splitter)→DHT.
  Self-hosted bootstrap на нашем VPS остаётся верным решением.
- Isolated-замер оверхеда нашего транспорта (2026-09-11, checkip.amazonaws.com, 5 запросов):
  - direct через WG-инфраструктуру: **237 мс**/запрос;
  - через наш DHT-туннель поверх неё: **330 мс**/запрос;
  - ** overhead нашего туннеля ≈ +93 мс** — приемлемо; M5 (uTP/KCP) снизит далее.
- TC-09 «direct»-пробы к заблокированным хостам проходили через splitter — инconclusive
  объясняется этим; финальный кейс закрыт тестом через НАШ туннель (TC-12, HTTPS 200).
- Стратегия: WG-схема пользователя и PoC-транспорт — независимые слои; сбой splitter'а
  деградирует их схему, но наш туннель (обнаружение через DHT, независимая точка входа)
  может работать как резервный путь и наоборот. Проверить при отдельной серии без WG.

## Результаты M5 — мультиплексированные сессии, протокол v2 (2026-09-11)

Протокол v2: у фреймов появились байт типа и streamId (`OPEN/DATA/CLOSE/PING/PONG`),
streamId 0 — сеансовый keep-alive (клиент шлёт PING каждые 20 с, сессия мертва после 30 с
без PONG). Exit демультиплексирует потоки в upstream TCP-соединения. Одна сессия несёт все
SOCKS-стримы. Сессии без активности >10 мин закрываются (на exit). Данные, приходящие между
SOCKS-хендшейком и открытием потока, буферизуются (фикс гонки с потерей запроса).

## Архитектура после M4

```
Приложение → SOCKS5 127.0.0.1:1080
                 ├─ правила proxy  → tunnel(client↔exit, AEAD-фреймы) → exit CONNECT host:port → цель
                 └─ правила direct → напрямую с машины (через WG/Beget-RU)
DNS: домен уходит на exit (socks5-hostname) → резолв на NL, без локального отравления
```

## Итог

M1–M4 выполнены: обнаружение exit'а через публичный BitTorrent DHT (self-hosted bootstrap против
фильтрации), AEAD-фреймовый дата-канал, SOCKS5 с удалённым DNS, split-tunneling по правилам.
Подтверждён доступ к заблокированному ресурсу по настоящему HTTPS.
Следующие этапы: M5 (uTP/KCP дата-план — снижение RTT), mux (одна туннельная сессия на все потоки),
сервис-изация клиента (автостарт), мультипатчинг нескольких exit'ов.

## Как пользоваться (M4)

- curl: `curl --socks5-hostname 127.0.0.1:1080 https://<site>/`
- Браузер: SwitchyOmega/FoxyProxy → SOCKS5 `127.0.0.1:1080`.
- Правила: `MAGNETGATE_RULES=path` + JSON `{"direct": ["ru"], "proxy": []}` — при непустом `direct`
  всё, что не совпало, идёт напрямую (если задан `proxy` — наоборот, только он через туннель).
- Запуск клиента: `node client.js <psk> 1080` (env: `DHT_BOOTSTRAP`, `MAGNETGATE_RULES`).
